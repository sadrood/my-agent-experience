## 经过
用自研命令走完 QQ 机器人"扫码绑定"（POST q.qq.com/lite/create_bind_task → 二维码指向 q.qq.com/qqbot/openclaw/connect.html?task_id=… → 轮询 /lite/poll_bind_result），
拿到 bot_appid + bot_encrypt_secret（AES-256-GCM 解密：前 12B IV、后 16B tag、key 为本地随机 32B，与官方 @tencent-connect/qqbot-connector 的 decryptSecret 逐行一致），
凭据落进 .env 后启动桥（qq-botpy）。

## 失败点
`python -m agent.qqbot` 启动即报 `RuntimeError: {'code': 100016, 'message': 'invalid appid or secret'}`，
即腾讯 https://bots.qq.com/app/getAppAccessToken 拒绝这对凭据。间隔数分钟重试、以及**重新扫码换一把新 secret**（同一 appid、新 secret 确实不同）后仍 100016 → 不是偶发、不是生效延迟。
- 用 WorkBuddy 的 app.asar（v581/main/main/qq.js）交叉验证：它的连接方式与 botpy 完全一致（同一 token 端点、apiBaseUrl=https://api.sgroup.qq.com、appId+appSecret 明文传 JSON），排除"我们调用姿势不对"。
- poll 原始响应字段只有 bot_appid / bot_encrypt_secret / status / user_openid，没有遗漏字段。
- 解密结果 32 位可打印字符、格式正常，AES-GCM 解密若错会先抛 tag 校验异常。

## 结论与可复用步骤
扫码绑定只保证"把凭据取回来"，**不保证这对凭据能过开放平台鉴权**；判定方向应转向平台侧（机器人/开发者是否完成激活、认证、上线）。
排查顺序（由廉价到昂贵）：
1. 先用产品命令跑一次真实登录，拿到腾讯原始错误码（100016=凭据不被接受；4004/4006 之类是网关与会话问题，性质不同）。
2. 再做一次绑定并 dump poll 原始字段名+值长度（不打印 secret），确认没漏字段。
3. 别急着怀疑自己的解密/请求格式——去比对宿主（WorkBuddy/其它）的实现：同端点同参数就说明凭据是变量。
4. 让用户去开放平台核对 appid 是否在其机器人列表、是否需认证/上线；或直接重新创建机器人取标准 AppID/AppSecret。

## 坑
- 后台跑长驻 python 必须带 `-u`，否则 stdout 块缓冲，`bg output` 一直"暂无输出"，会误判进程没动静。
- 脚本放在子目录里跑要 `set PYTHONPATH=.`，否则 import 不到项目内包。
- 二维码要让用户扫：把 PNG 放大 3 倍再用 Start-Process 打开图片查看器，比终端 ASCII 画稳。
