【经过】给某 TMS 网站做测试用例表：先走查全站写出 62 条，之后对设备新增/删除做了界面实测，再回到用例表把实测细节补成 22 条（设备管理 19 + 资源命名 3），并把原先 NT 的「新建设备」改成 Pass。

【关键做法】
1. 用例表用**一个生成脚本**（openpyxl）维护：CASES 列表里每条一个 C(...) 调用，脚本一次产出三份产物——填好结果的 Case26 格式 xlsx、Markdown 版、以及清空「实际结果/是否通过/备注」的空白模板 xlsx。统计块与「总用例/Pass/Fail」全部由脚本按结果列自动算，不手改数字。
2. 新增用例用「插到生成标记之前」的方式追加（锚点 = 生成区的注释行），分块插入，每块 6-8 条，避免一次改太长被截断。
3. 每条用例的「实际结果」都回填**当时真的看到的现象**（含截图文件名、列表计数变化、后端错误码原文）；没实测的写 NT 并说明缺什么条件，不编。
4. 旧用例状态会过期：实测推翻了原先的「未实测/NT」判断时，要把旧条目一起改掉，否则表里自相矛盾。

【坑】
- edit 工具改 output/ 下的 .py 生成脚本会触发 preflight 跑全套 pytest（>180s）然后**回滚**改动；这类脚本改用 python 直接读写文件即可。
- 截图里的事实用本地 OCR 复核（对话框字段名、按钮文案、列表计数、SN 原文），比凭记忆写"实际结果"可靠得多。

【可复用步骤】走查 → 写生成脚本 + 用例清单 → 实测 → OCR 截图核对细节 → 回填实际结果 → 更新过期条目 → 一次跑脚本出三份产物 → 校验编号连续、条数=总数。
